# Chromatic

Chromatic 是一个基于 Compositor 的 AI 照片调色学习项目，目标是让 AI 分析照片、解释调色建议，并生成可以继续编辑的调整结果。项目同时用于学习如何构建 Agent。

当前处于原型阶段：照片分析已完成一次真实 DeepSeek 调用并保存结果；固定冷暖参数工具已能生成完整的 Compositor 工程副本，用户已确认暖色调整成功。两部分尚未连接成完整调色流程。

## 功能目标与验收标准

### 自动初步调色（目标，尚未完成）

输入一张照片和修图要求，AI 分析曝光、白平衡、对比度及色彩，提出调整方案，由程序校验后应用到 Compositor 工程副本。

验收标准：程序输出调色建议和理由，并生成能在 Compositor 中打开的调整后工程；用户开关调整图层，能够检查前后变化，原始照片和工程得到保留。

### 参考作品调色（目标，尚未实现）

输入原照片、已调色的参考作品和修图要求，AI 分析两张图片的差异，借鉴参考作品的冷暖、对比度、饱和度及阴影和高光色彩关系，制定适合原照片的调整方案。

第一版计划在请求中同时提供两张图片，无需先训练专用模型。照片的光线和内容存在差异，参考风格调色不承诺完全复制参考图的观感。

验收标准：程序说明借鉴了哪些色彩特征，并生成可编辑的调整后工程；用户通过前后对比和参考图，判断结果是否朝目标风格靠近。

## 预期工作流程

这是待逐步实现的流程：

```text
照片 + 修图要求 + 可选参考图
  → 模型分析并提出方案
  → Python 校验参数
  → 调色工具写入 Compositor 工程副本
  → 打开或渲染工程，查看结果
  → 用户反馈，必要时继续调整
```

模型负责理解和建议，工具负责执行调整，Python 程序负责连接各步骤、处理错误和保存结果。

## 第 ② 步：固定参数冷暖调色

此工具使用 Python 标准库，无需模型调用或 API 密钥。源工程需要包含且仅包含一个名为 `Test Color Balance` 的 Color Balance 图层。当前面向已检查的示例工程，尚未支持自动创建图层或遍历嵌套图层组。

在项目根目录运行以下命令，会生成一个新工程：

```bash
uv run compositor_tool.py --input ../demo.comp --output outputs/my-warm-demo.comp --warmth 0.5
```

- `--input`：源工程目录，支持绝对路径和相对于当前工作目录的路径。
- `--output`：尚不存在的输出工程，名称以 `.comp` 结尾，且不能位于源工程内部。
- `--warmth`：`-1` 到 `1` 之间的数值，正值预期偏暖、负值预期偏冷；`0` 将此图层的色彩偏移设为零，仍保留工程其他已有调整。

已有输出会被拒绝覆盖。再次实验时换一个输出名称。复制或写入期间若发生磁盘等 I/O 错误，可能留下不完整副本；失败信息出现时不要将该副本当作成功结果。

工具会替换副本中目标图层的色彩平衡设置，不是在原参数上累加。其他图层配置保留，原工程不写入。乘以 20 后使用 Python 的 `round()` 取整，因此非常小的数值可能得到相同结果；该幅度是实验约定，不是摄影色温单位。

已生成供检查的工程：

| 工程 | 冷暖值 | 预期方向 |
| --- | --- | --- |
| `outputs/warm-demo.comp` | `0.5` | 偏暖 |
| `outputs/cool-demo.comp` | `-0.5` | 偏冷 |

用户检查步骤：

1. 在 Compositor 中分别打开两份工程，确认照片和图层正常显示。
2. 开关 `Test Color Balance` 图层，对比当前照片变化；保留 `Test Curves` 的关闭状态。
3. 观察暖版和冷版是否朝预期方向变化，记录是否存在无变化、方向相反或明显异常。
4. 反馈检查结果后再决定下一步。程序生成成功不等于视觉验收通过。

`QuickLook` 资源随工程一起复制，没有重新生成预览；请以 Compositor 打开后的实际画布为准，不依赖 Finder 缩略图判断效果。

`demo.comp` 位于仓库外，本地照片和生成结果也不纳入版本管理。仅克隆仓库还不能复现当前本地实验环境，需要自行准备照片和包含指定图层的 Compositor 工程。

## 第 ③ 步：照片分析与结果保存

在项目根目录运行（新调用会上传指定照片并产生 API 用量）：

```bash
uv run main.py --image test.jpg --instruction "保持自然，稍微暖一点，不要过度饱和" --output outputs/my-analysis.json
```

`--image` 选择 JPEG，`--instruction` 是本次修图要求，`--output` 是新的 JSON 文件名。已存在的输出会在模型请求前被拒绝；再次实验需换一个名称。依赖尚未安装时先执行 `uv sync`；已有本地环境也可用 `.venv/bin/python main.py` 加上相同参数运行。

程序流程：检查输出位置 → 读取 JPEG 并进行 Base64 编码 → 读取 DeepSeek 密钥 → 请求模型 → 解析和校验 → 保存。JPEG 仅检查扩展名、大小（最多 32 MiB）和开头标记，尚未进行完整解码、尺寸检查或缩放。

请求设置了 90 秒网络超时、关闭 SDK 自动重试，并限定最多 4096 个输出 token。网络超时是网络操作的等待限制，不是精确的整个命令总时限。使用非思考模式返回简短的结构化建议；设置方式参考 [DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)，图片输入参考 [视觉接口文档](https://api-docs.deepseek.com/guides/vision/)。

JSON 文件包含三部分：

- `metadata`：由程序填写照片路径、照片 SHA-256、修图要求、模型名称及 UTC 时间；不保存密钥或图片 Base64。
- `analysis`：曝光、白平衡、对比度和色彩倾向的中文分析与建议。
- `adjustment_plan`：四项经校验的数值建议。此阶段尚未应用到照片；当前调色工具只支持冷暖。

写入使用 `x` 模式，保存时再次拒绝覆盖。若写入期间发生磁盘错误，可能留下不完整文件，需要检查错误提示；此阶段尚未实现原子写入。

本地真实调用结果保存在 `outputs/analysis-natural-warm.json`。输入要求是“保持自然，稍微暖一点，不要过度饱和”，返回建议为曝光 `-0.2`、对比度 `-0.1`、冷暖 `0.15`、饱和度 `-0.15`。这些是模型对本次照片的建议，不是固定预设；用户已检查并认为本次分析比较恰当，不代表对其他照片的通用效果保证。

用户验收：阅读分析是否符合照片，检查建议是否考虑修图要求，以及文字建议和参数方向是否一致。满意后再连接 Compositor 工具。

## Git 与 GitHub 的学习节奏

Git 提交是在本地保存可追溯的版本；GitHub 推送是把已提交的版本同步到远程仓库。每个小步骤经程序检查和用户验收后，提醒用户做一次有明确说明的本地提交；需要备份或分享已检查的进度时，再推送 GitHub。

提交前先检查文件列表和差异，明确选择代码与文档。阶段版本记录 `.gitignore`、`AGENTS.md`、`README.md`、`main.py`、`compositor_tool.py` 和早期实验脚本 `inspect_compositor.py`；原有已跟踪的项目配置和依赖锁定文件继续保留。

`.gitignore` 已排除 `.env`、`.venv/`、Python 缓存、`.DS_Store`，以及仓库根目录的 `test.jpg`、`manifest_test.json` 和 `outputs/`。忽略仅影响 Git 对未跟踪文件的选择，不删除本地文件。`test.py` 是 Base64 练习，本次暂不提交，仍保留在本地，因此 `git status` 仍可能显示它为未跟踪文件。

本次版本整理只创建本地提交，GitHub 同步留到用户检查后单独进行。可在终端查看：

```bash
git log -1 --oneline
git show --stat HEAD
git status --short
```

第一条显示最近提交的编号和说明；第二条显示该提交涉及的文件；第三条显示尚未提交或尚未跟踪的内容。`HEAD` 在这里表示当前检出的提交。忽略规则中的照片和工程输出不会出现在普通状态列表中，但仍可在本地使用。

## 学习与开发顺序

每一步先讲解，用户批准后施工，施工后等待用户检查。

1. 建立项目协作规则、功能目标和当前状态说明。
2. 用固定参数验证 Compositor 工程副本能够打开并显示调整结果。
3. 核对模型配置，获得并保存照片分析结果。
4. 连接分析与调色工具，完成自动初步调色。
5. 增加参考作品输入和风格调色。
6. 完善前后对比、一次用户反馈调整和演示验证。

阶段目标是在一到两天内争取完成范围受控的可演示版本，同时逐步理解代码与 Agent 工作流程；实际范围根据每一步的检查结果调整。
